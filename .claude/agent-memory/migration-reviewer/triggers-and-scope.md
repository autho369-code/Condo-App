- Triggers on `public.portfolios` (same-timing fire alphabetically): BEFORE INSERT `portfolios_guard_domain_verification`, `trg_generate_portfolio_slug`; BEFORE UPDATE `portfolios_guard_domain_verification`, `portfolios_guard_platform_columns`, `trg_portfolios_updated`. Baseline triggers are in `20260715040000_production_schema_baseline.sql` (uppercase quoted `ON "public"."portfolios"`).
- payable_bills RPC scope pattern (20261007080000): after can_manage_finance add `can_view_association_row(association_id)` ('Bill not found') + `operator_may_write(false)`; can_view_association_row returns true for null association, so null-association bills stay reachable (matches RLS).
- Finance RPC scope (20261007090000): association source per RPC = row's association_id, `unit_association_id(unit)` for charges, bank_accounts + payable_bills for check runs (patch the `record_check_run` wrapper; `_legacy` is not client-callable). Most of these tables already have `<table>_association_scope` row triggers (20261004130000), so RPC checks are defence-in-depth. Cron calls `generate_*` workers, not the user RPCs; no auth.uid means `manager_is_scoped()` is false, so jobs pass. Internal callers of `create_payable_bill`: `bill_purchase_order`, CSV bill import (same caller identity).
- Maintenance/calendar RLS map (as of 20261008020000): maintenance_tasks/history policies were rebuilt in 20260726040000:1150-1225 (history WITH CHECK requires `completed_by is null or = auth.uid()`); restrictive layers: mgr_assoc_scope (tasks+calendar_events), staff_association_in_company_insert/update (calendar_events, 20261005040001), operator_writes_need_admin (tasks+history, 20261005070000), board read = false (20261005111000). calendar_events triggers (move_private_fields, maintenance/sms notify) are SECURITY DEFINER and no-op unless notify_* true. `calendar_events_title_check` is length 1..200 and task_name has no length CHECK: an RPC that builds `prefix || task_name` should `left(...,200)`.
- Triggers on `public.associations` (as of 20261008030000), BEFORE row fire alphabetically: `associations_move_private_fields` (ins/upd of management_end_reason, maintenance_notes, description; writes association_private/vendor_private, nulls cols; never touches portfolio_id/property_group_id), `associations_property_group_same_company` (ins/upd of property_group_id, portfolio_id), `trg_associations_set_slug`; statement-level `operator_write_guard`; AFTER `trg_ensure_bank_accounts` (insert), `trg_log_soft_delete` (archived_at). associations.portfolio_id is nullable. property_groups_admin_all lets an admin of both portfolios move a group's portfolio_id (no reverse trigger).
- Vendor same-company triggers: work_orders `work_order_vendor_in_company` (20261005030001, no locks, skips unchanged UPDATE, 23514); calendar_events `calendar_event_vendor_in_company` (20261008040000, FOR SHARE on associations+vendors, uses association's company first). FOR SHARE (not KEY SHARE) is needed to block a portfolio_id move but blocks ordinary association/vendor UPDATEs until commit: low, note lock-upgrade deadlock only if a txn locks-then-updates the same association.
- Lock tables (20261008080000 import_locks): check (a) stale-takeover DELETE is pinned to the checked association (invoker + RLS, safe), (b) client-settable `claimed_at` lets a staff user insert a far-future lock that never goes stale (policy needs `claimed_at <= now()`), (c) release by user id can drop the same user's newer takeover lock; suggest a claim token.
- Owners/occupancies triggers (as of 20261009010000): BEFORE UPDATE on owners fire `owners_move_private_fields` (of notes) -> `trg_owners_000_self_service_guard` (new:=old for portal callers, skips at trigger depth>1) -> `trg_owners_set_portfolio_from_association`; AFTER `owners_move_private_fields_insert`, `trg_dispatch_owner`, `trg_log_soft_delete`, `trg_owners_audit`. Occupancies: `occupancies_association_scope` (20261004130000), `occupancies_move_private_fields`, `trg_occupancies_000_self_service_guard`, `trg_occupancies_sync_unit_owners`, `occupancies_cancel_autopay_on_end`. Nothing checks occupancies.association_id against the unit's building, and unit_owners has no association check (transfer_unit_ownership only checks portfolio).
- mgr_assoc_scope on owners/owner_private (20261009010000, 2026-10-09): only `manager_is_scoped()` = hoa_role 'manager' + association_managers row is narrowed; portal/board/admin/operator unaffected; definer triggers/RPCs bypass RLS (postgres owner). Restrictive FOR ALL with only USING also acts as WITH CHECK on insert/update. Trigger SELECT ... FOR SHARE needs no grants/policies when the trigger is SECURITY DEFINER (invoker would need UPDATE privilege + UPDATE policy).
- Lock-order pattern to check: BEFORE UPDATE trigger runs after the row lock is taken, so "child row lock -> FOR SHARE parent" vs "parent UPDATE -> AFTER trigger updates children" can deadlock (40P01). Example: owners update of association_id/portfolio_id vs associations company move (20261009010000:155 vs :346). Low when the parent move is rare.
- Portal auto-link order: `auto_link_portal_user` fires AFTER INSERT on auth.users, i.e. BEFORE `link_vendor_on_invitation_accept` (20261005113500, newest match, ignores user_invitations.association_id). With one record per association, "oldest" auto-link wins and can bind the login to the wrong association's record.
- BEFORE triggers fire alphabetically: `trg_vendor_*` sorts before `trg_work_order_*`; check no later-sorting trigger fills the column a guard reads (work_orders.association_id is NOT NULL, nothing fills it as of 2026-10-09).
- auth.users AFTER INSERT trigger order: trg_apply_pending_invitation (inserts profile, then marks invitation accepted -> user_invitations AFTER UPDATE triggers fire here) -> trg_auto_link_portal_user -> trg_handle_new_auth_user. accept_invitation (signed-in) updates the invitation BEFORE the profile, so invitation triggers see the OLD profile, and it overwrites profiles.hoa_role (board -> owner downgrade when a board member accepts an owner invite).
- 2026-10-10: a migration that creates a company-data table must also attach `operator_write_guard` (per-table statement trigger); #275's company_state_rules shipped without it (fixed 20261010020000). Flag its absence.
