- Invitation emails: `queue_invitation_email` (20260731010000) skips rows with `metadata.email_delivery = 'application'`; `invite_staff` relies on the `hoa_role` default 'manager'. Email URLs: auth links use slug host (`tenantWorkspaceUrl`), never custom domain.
- `user_invitations.token` writers (as of 20261007040000): column default (2x uuid sans dashes = 64 hex) and `generate_invite_token()` (hex of 32 bytes); no app insert/update sets `token`. A token CHECK is safe; re-grep `from('user_invitations')` and SQL `insert into public.user_invitations` for a `token` column if it changes.
- `portfolios.company_name` writers (as of 20261007050000): SQL `provision_portfolio` (20261005010001:80, untrimmed, app trims first), `update_company_profile` (20261001171941, rejects blank), legacy `invite_company_admin`/`platform_create_company` (baseline :4918/:5921, unused by app); app: `app/platform-operator/companies/actions.ts` (:87 create, :660 edit), `app/(app)/settings/branding/page.tsx`, `lib/rpcs/portfolio.ts`. All reject blank before writing.
- imported_balances writers: `import_opening_balance` (20261003120000, invoker; charge due_date = p_as_of) from CSV opening-balance import and the AppFolio AR import (`app/(app)/owners/import/appfolio/receivables-actions.ts`), which since 2026-10-08 dates every row of a run with the report's as-of date (charge date kept in memo), so 20261008070000's unit+as_of_date grouping is right per run. Residual: one unit imported at two different as-of dates compares system balance (includes earlier imports) to only the later group's sum; a cumulative per-unit window sum fixes it (low).
- Receivables GL facts (2026-10-09): charge Dr A/R / Cr income, payment (method 'credit') Dr payments.gl_account_id / Cr A/R, both via post_subledger_entry (insert posted=false then update posted=true, so `trg_guard_closed_period` raises for closed months on charges and payments alike). New payments auto-apply via `trg_auto_apply_payment` -> apply_payment (ownership period of payment_date); new charges via `auto_apply_credit_on_new_charge` (same period). post_homeowner_credit requires a non-blank memo; `trg_payments_gl_permission` checks can_use_gl on payments.gl_account_id (charges skip it when the category has no GL).
- GL mapping keys (as of 20261013080000): `gl_account_map.map_key` CHECK + `set_gl_account_map` type rules + `lib/gl/accounts.ts` list allow only accounts_receivable, accounts_payable, late_fee_income, default_income, assessment_income, undeposited_funds. A new `app_gl_map(..., '<key>')` branch with any other key is dead code until all three are extended (20261013080000:46 'nsf_fee_income').
- Payment reversal (reverse_homeowner_payment, 20261003080000) inserts an 'other' reversal charge FIRST (due_date = p_reversal_date, backdatable to >= payment_date, or future), then sets payments.reversed_at=now()+reversal_charge_id (fires trg_payments_recheck_payment_plan). Credits cannot be reversed. No app path edits payments amount/unit/date; the update trigger fires mostly on reversals.
- Payment plan triggers: payments INSERT -> app_complete_paid_payment_plan (active only, completed_at=now()); payments UPDATE(amount,unit_id,method,payment_date,reversed_at)/DELETE -> app_recheck_payment_plan (reopen clears completed_at). NOTHING rechecks on charges insert/delete. payments/charges.created_at default now(). Crons post dues 11:00 UTC, late fees 11:10 UTC (due today). report_data_payment_plans, payment_plan_schedule and both plan triggers all use payment_plan_paid_amount (report since 20261013210000).
- bank_reconciliations writers (2026-10-12): only app/api/bank-reconciliation/{create,complete,toggle-cleared}; create rolls back draft recons by deleting items+recon; no app void/reopen path. Purge pauses all triggers. Staging seed/cleanup scripts write completed recons directly. All recon FKs are NO ACTION except items.reconciliation_id CASCADE. Guard 20261013080000 is UPDATE/DELETE only, so INSERT of status 'completed' skips its balance check.
- Recon guards v3 (20261014170000, reviewed 2026-10-13): definer guards recompute ending_book_balance (app_bank_book_balance, no RLS) and item amounts; JS bookBalance uses INVOKER journal_line_totals, so they differ only under RLS. Gaps found: item type not derived (journal-line item typed 'bank_only' or the same line inserted twice skews the completion check; no unique (reconciliation_id, journal_line_id)); status 'void' is not terminal (void->in_progress/completed skips the insert-time date/one-open checks); no index on items.journal_line_id for the per-row 'already cleared' check. Column guard trigger app_guard_function_owned_columns blocks current_user authenticated/anon on bank_accounts.last_reconciliation_date + payments.bank_deposit_id; all SQL writers (create/void_bank_deposit, recon-date trigger) are definer. fund_type now forced from purpose for operating/reserve/special_assessment.
- Charge GL dating (20261014080000, reviewed 2026-10-13): `charge_ledger_date(charge)` = due_date, but fine/late_fee/nsf_fee post on least(due, association-local created_at date). Reversal uses charge_ledger_date(old), which matches the original only because created_at + the association zone don't change; entries posted under the old due-date rule (0 in prod then) would reverse on a different day. Twin not updated: `backfill_receivables_to_gl` (20260930020000:206) still dates by due_date. Earlier date = closed-period guard bites sooner on edits/unit moves of these fees.
- Violation hearing clocks: advance_violation's fine gate counts hearing_request_days from notice_sent_at (FIRST notice, 20261002173419); request_owner_violation_hearing (20261014080000) counts from coalesce(last_step_at, notice_sent_at), and every step incl. fine steps bumps last_step_at. Two clocks: ask which notice opens the window (steps carry offers_hearing) and that both use one anchor.
- Meeting quorum (20261014100000, reviewed 2026-10-13): calculate_meeting_quorum (definer, authenticated) reads for staff/owners but writes quorum_met/quorum_requirement/total_units only when can_edit_association_mvp (same gate as meetings_staff_update) and status scheduled/in_progress; publishMeetingMinutes records it before completing. Callers: that action + record_meeting_attendance (`perform`); none reads the JSON. Drift to watch: RPC counts owners with occupancies.status='current' (at publish time), but meetings/[id]/page.tsx counts owners by the meeting-date window, so a sale between meeting and publish changes the recorded result. quorum_requirement doubles as "manager-set" and "recorded"; new meetings always store it at creation.
- Meeting quorum v2 (20261014130000): calculate is read-only; trg_meetings_record_quorum_on_complete (BEFORE UPDATE OF status, old<>completed) records; trg_meetings_keep_completed_result (BEFORE UPDATE, old=completed) locks status+3 quorum cols unless public.app_is_repair_session(). Both UPDATE-only: an editor can still INSERT a meeting already 'completed' with any quorum, or DELETE a completed one (attendee cascade passes the lock: parent row gone). Legacy completed rows with NULL requirement/total_units are counted live, so start_time/association edits still move them.
- approval_requests status writers (20261014150000, reviewed 2026-10-13): guard trg_approval_requests_approve_guard lets 'approved' only via GUC app.approval_decision='on' (record_approval_decision, tally_approval_vote) or app_is_repair_session(). Other writers: cast_board_approval (revoked from authenticated in 20261005111000, dead), cancel_purchase_order ('cancelled'), request_payable_bill_approval/PO create ('pending' inserts), app approvals/new (insert 'pending'). approval_votes is written only by platform operator (approval_votes_platform_all); tally has no status='pending' check, so a whitelisted tally can flip rejected/cancelled -> approved. payable_bills and purchase_orders have insert/update/delete revoked from authenticated, so approval_request_id can't be relinked by users.
- Payment-date rules (20261014150000): record_bill_payment + record_check_run_legacy check bill_date <= date <= association_local_date(assoc, now()) + 90 per bill (association_local_date is granted to authenticated). Not covered: pay_owner_payable, recurring/PO-generated bills (no dup-invoice check either).
- Reconciled-item guards (20261015020000, reviewed 2026-10-13): every GL posting function does insert lines then  (~20 writers), so a BEFORE UPDATE guard on journal_entries that does per-line lookups runs on every posting; skip when old.posted is false. bank_reconciliation_items has there WAS no index on journal_line_id / bank_adjustment_id (added in 20261015020000) (only (reconciliation_id, x) uniques) and bank_adjustment_id has an FK (bank_reconciliation_items_bank_adjustment_id_fkey EXISTS; the "no FK" note was wrong). No SQL writer updates journal_lines; definers only change journal_entries.source_id / reversed_by_entry_id on posted rows. Item amounts are pinned at insert, so an edited bank_adjustment on an in-progress (or undone) recon leaves item.amount stale for the completion check. app_bank_book_balance filters jl.association_id, so a line guard must cover association_id too. (Fixed before apply: anchor, indexes, draft early-return, association_id, adjustment refused on any open reconciliation.)
