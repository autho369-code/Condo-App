- Bulk-delete/purge functions (20261009005000 delete_association_completely, reviewed 2026-10-09): `alter table ... enable trigger user` re-enables INTENTIONALLY disabled triggers: `trg_vendor_compliance_sync` is disabled on purpose (20261002131203:7, vendor self-certification fix). Save/restore `pg_trigger.tgenabled` per trigger instead. Also check: journal entries span associations (bank transfers between associations' accounts, 20261003190000:81), so "entries with a line in A" deletes B's lines (journal_lines.entry_id CASCADE); bank_reconciliation_items.journal_line_id is no-action (baseline :18883); DISABLE TRIGGER takes SHARE ROW EXCLUSIVE on every table it touches. Owner/global cleanups must be portfolio-scoped (multi-tenant).
- Purge re-review (20261009005000, 2026-10-09): `purge_blocking_children` on bank_accounts hits `associations.operating_bank_account_id`/`reserve_bank_account_id` (NO ACTION, baseline :18758/:18778; set for EVERY association by ensure_operating_and_reserve_accounts :4124), so it deletes the association itself early (and any other association pointing at those accounts). Generic "delete every no-action child" helpers must refuse on core tables. Quick FK map: parse baseline `ALTER TABLE ONLY ... FOREIGN KEY ... ON DELETE` with a scratch script, then grep later migrations for `references public.<t>`.
- One-level purge helpers (purge_blocking_children) miss grandchildren: bank_deposits <- payments.bank_deposit_id / other_receipts.bank_deposit_id (NO ACTION, 20261003170000:35), payment_intents <- stripe_autopay_runs / payment_processor_adjustments, bank_adjustments <- bank_reconciliation_items, autopay_mandates <- stripe_autopay_runs. Also bank_accounts has a THIRD associations link: `stripe_settlement_bank_account_id` (20260726010000:66, NO ACTION). FK closure script: parse baseline ALTER TABLE ONLY + later `references public.x` lines, compute cascade closure and NO ACTION/RESTRICT grandchildren.
- FK ON DELETE CASCADE from a parent (e.g. owners.association_id -> associations) silently extends a hard delete to many child tables; owners has 2 NO ACTION children (owner_payables, payment_intents) that then block the parent delete. Check the reverse FK list (baseline `REFERENCES "public"."owners"`).
- Polymorphic (<x>_type, <x>_id uuid) tables in public (snapshot 2026-10-09): audit_logs, automation_flow_runs(subject), data_diagnostics, documents, journal_entries(source), permission_audit_log(target_entity), record_notes, shares(resource), signature_requests(subject), sms_consent_events, sms_conversations(with_entity), sms_opt_ins, soft_delete_log, tag_assignments, violation_cases(violation). A catalog-driven "delete what points at deleted ids" pass hits journal_entries.source_id and deletes whole entries (lines CASCADE) with no shared-books check, and wipes audit/permission/soft-delete logs (20261009005000:162).
