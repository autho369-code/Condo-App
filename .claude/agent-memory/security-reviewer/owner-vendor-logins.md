## Owners belong to one association (2026-10-09 review, uncommitted diff)
- `owners.association_id` (20261009010000) + trigger `occupancies_owner_same_association` compares the owner to `occupancies.association_id`, which is caller-chosen: nothing ties it to `unit_association_id(unit_id)` (RLS `occupancies_staff_all` and `enforce_row_association_scope` both read the column). `unit_owners` (`can_access_unit` only) has no owner check at all. Any "owner X may only touch unit Y" rule must derive the association from the unit and cover `unit_owners` too.
- Dropping UNIQUE `idx_owners_auth_user` lets `auto_link_portal_user` link one sign-in to every same-company owner row with that email; helpers that use `owners.auth_user_id = auth.uid()` directly then widen to all of them. (2026-10-09: `can_view_association_mvp` no longer exists live; `owner_open_emergencies` and `form_templates_owner_read` use current_owner_ids()/resident helpers; the last two direct matches, the shared association files policy and `can_access_association_mvp`, moved to current_owner_ids() in 20261009070000.) Watch email dedupe scope in importers/creators.
- `associations_staff_all` allows DELETE; an `on delete cascade` FK from a core table to associations turns a PostgREST delete into a silent wipe. Prefer `restrict`.

## Vendors belong to one association (2026-10-09 review, 20261009020000)
- `can_view_association_row(null)` is TRUE for scoped managers, so any restrictive `mgr_assoc_scope` on a nullable association column lets them write the null (company-level) value. `vendors.is_management_company` (association null) is gated only in the app (`createVendor`); a scoped manager can insert/flip one via PostgREST, and the move guard skips management vendors. Look for this "null = company-wide" escape on every new nullable-association flag.
- `trg_vendor_same_association` covers only tables with both vendor_id and association_id; child tables without association (`work_order_estimates`, `lock_box_assignments`, `document_requests`, `work_order_ratings`) need their own parent-based check. `addEstimate` (lib/rpcs/work-orders.ts:240) compares portfolio only; `estimates_vendor_read` then shows the row to that vendor.
- `import_bills` (20261009030000): vendor match limited to row association + management company, after `can_manage_association`. Its "not a vendor of that association" branch runs a company-wide `exists` in SECURITY DEFINER, so a scoped manager learns that a vendor name exists in an association hidden from them by `vendors.mgr_assoc_scope` (main's version leaked the same via company-wide match/count). Low; fix = gate the hint with `can_view_association_row(v.association_id)`. Check every DEFINER importer's "found elsewhere" hint for this oracle.

## One vendor login across associations (2026-10-09 review, 20261009040000)
- Login -> records = `vendors.auth_user_id` (first) + `vendor_portal_logins` (added by `link_vendor_on_invitation_accept` 2nd branch). App code must use `me.vendor_ids` and validate client record ids against it (`ownVendorRecord`/`workOrderVendorRecord` in lib/rpcs/vendor-submissions.ts). Column guards on vendors/work_orders are role-based (`is_self_service_caller`, `is_any_staff`), not `current_vendor_id()`, so widening policies to the set did not bypass them.
- `accept_invitation` marks the invitation accepted BEFORE updating the profile, so invitation triggers see the OLD profile role/portfolio.
- Gaps flagged: linkers that test only `vendors.auth_user_id is null` (invite 1st branch, `auto_link_portal_user`) ignore `vendor_portal_logins`, so one record can get two logins; staff have no way to remove a `vendor_portal_logins` row (no DELETE grant/policy/UI).

## One owner login across associations (2026-10-09 review, 20261009050000)
- Widening `owner_id = current_owner_id()` to `IN current_owner_ids()` while `unit_id`/`association_id` are checked against the UNION `current_resident_*_ids()` lets a multi-record login write rows as record A for record B's unit: `votes_insert_guard` (unique is ballot+owner) -> one vote per record on the same ballot; also amenity_res/approval_requests inserts. Correct pattern = `insurance_owner_insert` (occupancy exists tying owner_id to that unit/association). Check every widened WITH CHECK for this. FIXED in 20261009050000 (owner_record_matches tied into all 16 owner write policies; survey answers by the survey's association record).
- No owner equivalent of `vendor_invite_scope`: `user_invitations_staff_insert` + `mgr_assoc_scope(association_id)` let a scoped manager insert an owner invite with association null and metadata.owner_id of another association; `link_owner_on_invitation_accept` never compares the owner's association to the invitation. FIXED in 20261009050000 (owner_invite_scope + trigger requires o.association_id = new.association_id).
- `link_portal_user` still links the oldest same-email owner record at signup (invite without owner_id) and on every auth email change: email-match linking survives the "invitation only" rule. FIXED in 20261009050000 (owner branch removed from link_portal_user and relink_all; email change only unlinks).
- Company admins can UPDATE user_invitations (status/used_by/metadata) directly, firing accept triggers without accept_invitation's email check; and staff can write owners.auth_user_id directly (no column guard). Trusted roles, but note when a rule says "only via invitation". Partly fixed in 20261009050000: the owner link trigger requires the accepting login's auth email = invitation email.

## Owner login part 2 (2026-10-09 review, uncommitted diff, 20261009060000)
- Pattern that passed: portal writes take the record from the thing acted on (`ownerRecordForUnit`, occupancy `.in(owner_ids).eq(unit_id|association_id)`, survey's association) or validate a client `record_id` with `me.owner_ids.includes(...)`; service-client reads stay pinned by `.in('owner_id', me.owner_ids)`. `submit_owner_message` 4-arg overload checks `current_owner_ids()` + occupancy in the record's association. Grep `me\.owner_id\b` in app/portal + lib after such changes; remaining hits were reads/guards only.
- `checkLinkedRecords` checks owner-vs-association only when `associationId` is set; with association null (calendar events, management agreements allow it) any company owner passes (owners RLS is company-wide), so a scoped manager can attach an owner of an association they do not manage. Low; flagged 2026-10-09. FIXED in owner login part 2 (owner half: owner's association must pass managesAssociation); vendor half still open.
